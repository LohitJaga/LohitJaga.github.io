Memory Is the Harness: Probabilistic State for AI Coding Assistants

September 2026, updated October 2026 · gaussian-memory-worker

In July, the job that groups my memories into topics was broken. Every run gave different results, and my assistant's memory had a note saying so: don't trust the output. A few days later I fixed it, and now there were two notes about the same thing that disagreed. A plain vector store keeps both and returns whichever one happens to sit closer to your next prompt.

Gaussian Memory is an MCP server that gives Claude Code, Cursor, Codex, OpenCode and Zed persistent memory across sessions. It runs entirely inside your own Cloudflare account. When you save something new, it checks what's already there and decides whether it's a repeat, an update, or something new. Memories you keep coming back to get more confident, and ones you never touch fade.

Asking it today whether the rebuild is still broken returns this:

[1.72] (domain-rebuild-project ↑/episodic) 3mo ago • Changed domain rebuild status from unstable to current, exact, and done because user confirmed the fix
[1.69] (domain-rebuild-project ↑/episodic) 3mo ago • Fixed two bugs in domain rebuild: `targeted=false` param and rebuild continuation logic

The old "it's broken" memory doesn't come back. When the fix was saved, the system marked it as replaced, so Claude gets the current state instead of two answers that disagree.

The bottleneck moved

I've switched between Claude, a hosted GLM, and a quantized Llama under an open harness, and which model sits behind the editor matters less than it used to. All three hit the same wall: they don't know the state of my project.

Your repository tells the model what your code does. It doesn't tell it why. It contains nothing about:

  • the migration that is 60% done and breaks if anything touches it
  • the fix you tried in March that failed in production
  • the trade-off you settled late at night and never wrote down

Some of that reaches a commit message. Most of it lived in a terminal session that no longer exists, so every few days I typed it out again.

Why "just add RAG" doesn't finish the job

Semantic search works when you know what you're asking. "What did I decide about session storage" retrieves fine, because the query and the stored text share most of their meaning.

Real sessions don't open that way. They open with "where was I" or "fix that thing." Against a store of a few thousand memories, four words like that are roughly equidistant from everything you've worked on, so cosine similarity alone is mostly noise.

To check whether any of this helps, I wrote down 53 real questions I'd asked my own store and marked which memories should come back for each. Plain vector search finds the right memory 62% of the time. Gaussian Memory finds it 83% of the time, and it's usually near the top of the list. On the vague questions the gap is bigger, 92% vs 67%, but there are only 12 of those, so I wouldn't lean on it too hard. Questions that need several facts at once are still the weak spot at 61%. I measured all of this on my own data, so it's not a public benchmark yet. The test harness is in the repo if you want to run it on yours.

Most of the work happens at write time

Most memory systems store first and sort it out at read time. I moved the hard calls to the moment a memory is written.

Merge or keep separate. When a new memory lands close to an existing one, TypeSafe's Jev decision model classifies the pair as same, update, adds_detail, or different. A repeat gets merged and the original becomes more confident. Anything different is stored on its own. The mistake I most wanted to avoid is merging two different facts, because then one of them is just gone. On 160 labeled pairs Jev got 95% right and never did that.

Contradictions. An update flags the old memory for a second pass, where the judge decides supersedes, conflicts_with, extends, or compatible, with a confidence and a written reason. The verdict is stored as a relation between the two memories. Nothing is rewritten or deleted, but a supersedes verdict gives the older memory an end date, which takes it out of retrieval. The row stays next to the reason it was replaced, so you can always see what changed and why.

Keywords for later. Shortly after a memory is written, a background job has Llama 4 Scout generate the words you'd probably use when looking for this memory later. Those go into the keyword index, so a casual "the auth thing" can match a memory that never used the word auth.

Then ranking

A read goes through three steps.

1. Find candidates. Vector search and keyword search (SQLite FTS5) run in parallel, and their results are merged with reciprocal rank fusion.

2. Score them. Each candidate gets a weighted score:

base = 0.70·cosine + 0.15·bm25 + 0.10·recency + 0.05·access_frequency

That score is then multiplied by a Bhattacharyya term, clamped to [0.70, 1.40], which compares how uncertain the query is with how uncertain the memory is. This is where the confidence model comes in. It's skipped when the top match is already near-verbatim, since a clear match doesn't need help. When I turned it off in testing, the right memory ranked lower.

3. Rerank. Jev reads the top 80 candidates along with the end of the assistant's previous reply and puts them in order. The previous reply is what makes "fix that thing" work, since the prompt alone doesn't say what "that" is. It runs twice with the candidates in opposite orders and averages the results, because a single call is sensitive to position. This step made the biggest difference of anything I tried: the right memory moved from around second place on average to near the top.

There's one problem I haven't solved yet. Every read reinforces whatever it returns, so the memories that get used a lot all end up at maximum confidence. 44% of my store is sitting there right now. My benchmark freezes the store, so it can't see this, and I need a longer test to measure it.

Compared to Mem0 and Zep

Both handle contradiction. Zep tracks validity intervals on graph edges and invalidates contradicted facts. Mem0 runs an LLM pass at write time that decides whether to add, update or delete. Mem0's recent post on managing time in memory splits it into two clocks, when something happened and when it was stored, which is a good way to think about it.

The differences here: the merge and supersede calls go to a dedicated decision model instead of a general LLM extraction prompt, a replaced memory is kept rather than deleted, and every verdict keeps its reason. The gap on my side is event time. Gaussian Memory assumes a memory was true around when it was written. That holds for coding agents, where you store things as they happen, and breaks on something like a bulk import of old notes.

Reading the block

[1.69] (domain-rebuild-project ↑/episodic) 3mo ago • Fixed two bugs in domain rebuild: `targeted=false` param and rebuild continuation logic

1.69 is the final score, which can go above 1 because of the confidence multiplier. domain-rebuild-project is the project it was saved under. The arrow is how confident the system is in it: ↑ sharp, → holding, ↓ fading. episodic means it's something that happened, as opposed to a decision or a procedural note about how things work.

Runs in your own account

Giving an assistant memory shouldn't mean sending your session transcripts to someone else's server.

Gaussian Memory deploys as a single Worker into your own Cloudflare account. D1 holds the memories and their history, Vectorize handles dense search over 768-dimension BGE embeddings, and Workers AI runs the embeddings, extraction, and Jev. Jev bills through your AI Gateway credits at about $0.001 per prompt and is off until you turn it on; everything else fits the free tier. Nothing routes through me.

The cost is latency. A retrieve takes about a second server-side, and about three seconds for the hook's three parallel queries.

Capture is filtered before storage: read-only commands, git plumbing, installs and deploys are dropped, and it tries to redact anything credential-shaped on the way in (bearer tokens, provider API keys, JWTs, URLs with inline credentials, KEY=value secrets, PEM blocks). That's pattern matching, not a guarantee, so treat it as a safety net. Everything it kept is listable, editable and deletable.

Get it

One MCP server, same behavior in Claude Code, Cursor, Codex, OpenCode and Zed.

git clone https://github.com/LohitJaga/gaussian-memory-worker
cd gaussian-memory-worker && npm install
npx gaussian-memory init

The model in your editor will be a different model in six months. What carries over is whether it starts each session knowing your project or asking you to explain it again. I built this because I was tired of re-explaining my own projects to my tools.
