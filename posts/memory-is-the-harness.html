Memory Is the Harness: Probabilistic State for AI Coding Assistants

September 2026, updated October 2026 · gaussian-memory-worker

Every time I start a new session with a coding agent, I have to re-explain my project. Claude Code and Codex can read the repo, but the repo doesn't say what I already tried and dropped, or what I decided last week and why. Some of that ends up in a commit message. Most of it lived in a terminal session that's gone. The model only knows what the harness around it hands it, and memory is the part my harness didn't have.

Gaussian Memory is the memory server I built for this issue. It runs as a Cloudflare Worker in your own account. Because it's an MCP server, it works with coding agents like Claude Code, Codex, Cursor, OpenCode and Zed, but it isn't limited to coding tools. Any agent that can call MCP tools can use it, and the repo includes a LangChain wrapper so you can plug it into an agent you build yourself.

In Claude Code and Codex, it runs through a UserPromptSubmit hook, which fires every time you send a prompt and before the agent starts working on it. The hook searches the memory store for anything related to what you typed and passes those memories to the agent along with your prompt, so the agent already knows the relevant history when it starts. The agent can also call the memory tools on its own, for example to save a decision or look something up mid-task.

The name comes from how each memory is stored. Along with its embedding, every memory has a σ that tracks how confident the system is in it. The σ gets smaller when a memory keeps getting used or repeated, and it grows when the memory goes untouched for a while.

Storing memories is the straightforward part. The harder problems are finding the right memory when the prompt is vague, and knowing which memory is still true. This blog goes through both, using real data from my own store.

How a memory gets saved

Most of the work happens when a memory is saved, before anything is ever retrieved. Every new note goes through the same steps:

  1. The new note is embedded and compared to the closest existing memory in the same project.
  2. If the two are close (cosine 0.80 or higher), Jev, a decision model from TypeSafe that runs on Workers AI, reads both and picks one of four answers. same means the same fact in different words. update means the same subject, but something changed, like a number, a date, a status or a plan. adds_detail means new information that doesn't change anything in the old note. different means they're about different things.
  3. A same doesn't store anything new. The existing memory just gets more confident, and its text stays as it was so a shorter restatement can't overwrite a more detailed original. An update is stored and the old memory is flagged for the judge. adds_detail and different are stored on their own.
  4. Every night, the contradiction judge works through the flagged memories and the near misses for up to three minutes. For each pair it decides supersedes, conflicts_with, extends or compatible, with a confidence. Only a confident supersede (0.8 or higher) between two memories in the same project hides the older one. When it does, the judge also checks close rewordings of the old memory, like the four in the timeline above.
  5. The same nightly job has Llama 4 Scout write a few casual ways I might ask about each new memory later, plus some keywords, and adds them to the keyword index. That's how a vague "the auth thing" can match a memory that never says auth.

The mistake I cared most about avoiding was merging two different facts, because then one of them is just gone. On 160 labeled pairs, Jev got the relationship right 94% of the time and never merged two different facts. As the judge, it got 91% right on 120 pairs with known answers, against 86% for Llama 3.3 70B, at about a third of the latency.

How a memory gets found

When the hook or the agent asks for memories, the search runs in three steps:

  1. A wide first pass. Vector search pulls the top 100, and keyword search runs over the memories and the phrases the nightly job wrote for them. The keyword query also includes words from the end of the agent's previous reply, so "fix that thing" picks up whatever "that thing" was.
  2. A weighted score. The main terms are 0.70 vector similarity, 0.15 keyword match, 0.10 time since the memory was last used and 0.05 how often it's been used, plus smaller boosts for shared entities and dates. This is where σ comes in: when either the query or the memory has a high σ, a weaker match is penalized less, by a multiplier between 0.70x and 1.40x.
  3. A rerank. Jev reads the prompt, the end of the previous reply and the top 80 candidates in one call and picks the most useful ones, about ten. Its top pick changed about a third of the time when I reversed the candidate order, so it runs both orders and averages them.

Before Jev, I tried a cross-encoder and HyDE, and the second memory in the example above is the record of why neither one shipped. Jev adds about 0.6 seconds to each prompt, which I think is worth it for getting the right memory back.

Does it work

To measure this, I wrote 53 questions against my own store and labeled which memories should come back for each one. Then I ran them against the live deployment and against plain vector search, with about ten results each. Recall is how often the right memory came back at all, and MRR is how high it ranked, where 1.0 means it was always the first result.

I also replayed 250 real prompts from my own sessions through the full hook. The first memory it added to the context was useful 74% of the time, up from 53% with the pipeline before Jev, and a useful one was in the top three 92% of the time. The eval only lets the system see memories that existed before each prompt, so it can't do better by finding notes from the future.

This is all my own data, not a public benchmark. The vague set is only 12 questions, so I wouldn't lean on that row too hard, and questions where the answer is split across several memories are still the weak spot. The test harness is in the repo if you want to run it on your own store.

Runs in your own account

Everything runs in your own Cloudflare account. D1 holds the memories and their history, Vectorize handles vector search over 768-dimension BGE embeddings, and Workers AI runs the embeddings, the extraction and Jev. Jev bills through your AI Gateway credits at about $0.001 per prompt and is off until you turn it on. Everything else fits in the free tier for a few thousand memories. Nothing goes through me.

The tradeoff is speed. A reranked read takes about three seconds warm, and the hook runs three of them in parallel before the agent answers, so every prompt waits on that.

The hooks filter what gets captured. Read-only commands, routine git commands, installs and deploys are dropped, and they try to redact anything that looks like a credential before it's stored. Everything it keeps can be listed, edited and deleted.
