Memory Is the Harness: Probabilistic State for AI Coding Assistants

September 2026, updated October 2026 · gaussian-memory-worker

Every time I start a new session with a coding agent, I have to re-explain my project. Claude Code and Codex can read the repo, but the repo doesn't say what I already tried and dropped, or what I decided last week and why. Some of that ends up in a commit message. Most of it lived in a terminal session that's gone. The model only knows what the harness around it hands it, and memory is the part my harness didn't have.

Gaussian Memory is the memory server I built for that. It runs as a Cloudflare Worker in your own account and works with Claude Code, Codex, Cursor, OpenCode, Zed, and anything else that supports MCP. On every prompt, a hook looks up the relevant memories and adds them to the context. The agent can also call the memory tools directly. The name comes from how each memory is stored: an embedding plus a σ for how sure the system is about it. σ shrinks when a memory gets used or repeated and grows when it doesn't.

Saving memories is the easy part. The two hard parts are finding the right one when the prompt is vague, and knowing which one is still true. This post goes through both using real data from my own store.

When a fact changes

In early July, the job that sorts my memories into topics was unstable. Every run landed on a different number of topics. On July 5 the system saved this:

No new ship date set yet.

The fix was splitting topic labels and clusters into two separate mechanisms, after which the rebuild gave the same answer every run. On July 7 the system saved this:

stored 2026-07-07 · episodic

The domain rebuild instability issue (wildly different domain counts run-to-run, false-positive/negative merges) that caused the July 1 ship delay is resolved as of 2026-07-05 — domain and cluster_id were split into separate mechanisms, rebuild is now deterministic and reproducible.

Now there are two memories about the same thing that disagree. A plain vector store keeps both, and when I ask whether the rebuild still works, whichever one ranks higher wins. The agent has no way to tell that one of them is out of date.

What makes this pair tricky is that an embedding model doesn't see them as very similar. Their cosine similarity is under 0.70, so vector search alone never put them next to each other. What they share is words: domain, rebuild, instability. The contradiction judge looks for candidate pairs with both vector search and keyword search, and keyword search is what caught this one. This is the row it wrote:

Memory B is the July 7 one. The older memory gets an end date and stops showing up in search. Being replaced doesn't delete it, so the row and the verdict are still there if I want to see what changed. Asking today whether the domain rebuild is still unstable, the July 7 memory comes back and the July 5 one doesn't:

[1.25] (gaussian-memory ↑/episodic) 3mo ago ● The domain rebuild instability issue (wildly different domain counts run-to-run, false-positive/negative merges) that caused the July 1 ship delay is resolved as of 2026-07-05 — domain and cluster_id were split into separate mechanisms, rebuild is now deterministic and reproducible.

That line is exactly what the agent sees. 1.25 is the score it was ranked by. gaussian-memory is the topic it was sorted into. The arrow and the dot both show how sure the system is, on slightly different cutoffs: ↑ → ↓ and ● ◑ ○ go from sure to fading. episodic means it's something that happened, as opposed to a decision or a note about how something works.

How a new memory gets saved

Most of the decisions happen at write time.

  1. The new note is embedded and compared to the closest existing memory.
  2. If the two are close (cosine 0.80 or higher), Jev, a decision model from TypeSafe that runs on Workers AI, reads both and picks one of four answers. same means the same fact in different words. update means the same subject, but something changed, like a number, a date, a status or a plan. adds_detail means new information that doesn't change anything in the old note. different means they're about different things.
  3. A same doesn't store anything new. The existing memory just gets more confident, and its text stays as it was so a shorter restatement can't overwrite a more detailed original. An update is stored and the old memory is flagged. From then on, reads show the old one with [CONTRADICTED — re-evaluate] in front and rank it lower, until the judge decides the new one replaces it. adds_detail and different are stored on their own.
  4. Every night, the contradiction judge picks up to 20 queued memories (near misses from saving, or flagged ones once that queue is empty), finds candidates for each with vector and keyword search, and labels each pair supersedes, conflicts_with, extends or compatible with a confidence. Only supersedes hides the older memory.
  5. The same nightly job has Llama 4 Scout write three casual ways I might ask about recent memories later, plus five keywords each, for up to 100 memories a night. Those go into the keyword index. That's how a vague "the auth thing" can match a memory that never says auth.

The mistake I cared most about avoiding was merging two different facts, because then one of them is just gone. On 160 labeled pairs, Jev got the relationship right 94% of the time and never merged two different facts. If Jev is turned off or takes longer than a second, saving falls back to merging only near-verbatim repeats.

Jev also replaced Llama 3.3 70B as the judge. On 120 pairs with known answers, Jev got 91% right and Llama got 86%. Most of the gap is that Jev is better at not calling added detail a replacement, which matters because a wrong supersede hides a memory that was still true. It's also faster, about 330 ms per pair compared to 1.1 s. Llama is still there as the fallback, and it's the model that judged the July example, since Jev came in October. One tradeoff: Llama writes a sentence explaining each verdict, like the one above, and Jev verdicts right now only store the label and the confidence.

How a memory gets found

Specific questions are easy. "What did I decide about session storage" shares most of its words and meaning with the memory that answers it, so plain vector search gets it. Most of what I actually type is vaguer, like "where did you land on that" or "fix that thing". Those have almost nothing in common with the memory that answers them, so vector search mostly returns noise.

A read goes through three steps:

  1. A wide first pass. Vector search pulls the top 100, and keyword search runs over the memories and the phrases the nightly job wrote for them. The keyword query also includes words from the end of the agent's previous reply, so "fix that thing" picks up whatever "that thing" was.
  2. A weighted score. The main terms are 0.70 vector similarity, 0.15 keyword match, 0.10 time since the memory was last used and 0.05 how often it's been used, plus smaller boosts for shared entities and dates. This is where σ comes in. When either the query or the memory has a high σ, a weaker match is penalized less, by a multiplier between 0.70x and 1.40x. It's skipped when the top match is already near-verbatim. When I tested turning it off, before the rerank step below existed, the right memory ranked lower.
  3. A rerank. Jev reads the prompt, the end of the previous reply and the top 80 candidates in one call and picks the most useful ones, about ten. When I reversed the order of the candidates, its top pick changed about a third of the time, so it now runs both orders and averages them. If Jev takes longer than 2.5 seconds, it falls back to the first-pass order instead of making you wait.

Jev is opt-in because it costs money, and with it off, saving skips the Jev merge decision and reads skip the wide pass, the extra phrases, the previous-reply keywords and the rerank. The numbers below are with it on.

I tried two other rerankers before Jev. A cross-encoder was slower and found fewer of the right memories. HyDE, where a model writes a fake answer and you search with that, added almost 400 ms and didn't improve anything. Jev adds about 0.6 s per prompt. I think that's worth it.

I also replayed 250 real prompts from my own sessions through the full hook. The first memory it added to the context was useful 74% of the time, up from 53% with the pipeline before Jev. A useful one was in the top three 92% of the time, up from 77%, and the amount of irrelevant text it added went down 44%. The eval only lets the system see memories that existed before each prompt, so it can't do better by finding notes from the future.

This is all my own data. I haven't run a public benchmark yet. The vague set is only 12 questions, so I wouldn't lean on that row too hard. Questions where the answer is split across several memories are still the weak spot. The test harness is in the repo so you can run it on your own store, but the labeled questions aren't, because they're built from my personal memories.

What's still wrong

The judge doesn't check projects before comparing two memories. Of the 16 supersede verdicts in my store, only a few are real contradictions like the domain rebuild. Most are near-duplicates getting cleaned up, which is fine. But one retired a note from a different project because it looked like a new one. I haven't fixed that yet.

Confidence also drifts. Every read reinforces whatever it returns, including the background lookups the hook does on every prompt, so the memories that get used a lot all end up at maximum confidence. 44% of my store is sitting there right now. My benchmark freezes the store, so it can't see this. I need a longer test to measure what it does to ranking over time.

It's also not fast. A reranked read takes about three seconds warm, and the hook runs three of them in parallel on every prompt before the agent answers.

Compared to Mem0

Mem0 wrote about managing time in memory in their In Context newsletter on October 20, and it's a good breakdown of the problem. They split it into two clocks: when something happened and when it was stored. When a new memory replaces an old one, Mem0 keeps both and marks the old one as superseded, and a default read still returns both unless you ask for latest_only. It also supports expiration dates, resolving phrases like "last weekend" against when the conversation happened, and searching as of a past date.

Gaussian Memory makes the opposite default choice. A replaced memory is kept, but it's hidden from normal reads, so the agent gets the current answer without having to ask for it. The replace decision goes to a dedicated decision model rather than a general extraction prompt.

The part Gaussian Memory doesn't do yet is event time. It assumes a memory was true around when it was written. That holds for coding agents, where things get saved as they happen, but it would break on something like importing a year of old notes at once. It also doesn't resolve relative dates or expire memories on a date. That's the next thing I want to build.

Runs in your own account

Everything runs in your own Cloudflare account. D1 holds the memories and their history, Vectorize handles vector search over 768-dimension BGE embeddings, and Workers AI runs the embeddings, the extraction and Jev. Jev bills through your AI Gateway credits at about $0.001 per prompt and is off until you turn it on. Everything else fits in the free tier for a few thousand memories, until you hit Vectorize's storage limit. Nothing goes through me.

The hooks filter what gets captured. Read-only commands, routine git commands, installs and deploys are dropped, and they try to redact anything that looks like a credential, like bearer tokens, API keys, JWTs, URLs with passwords in them, KEY=value secrets and PEM blocks. It's regex, so it will miss things, and it only covers what the hooks capture, not notes the agent stores directly. Everything it keeps can be listed, edited and deleted.
